⚠ 注（计费敏感）："Engine failure"指服务端内部错误导致请求未能正常完成，如：OOM（GPU 显存不足）、CUDA 错误、模型加载失败、生成中途崩溃（返回 HTTP 500/503）。若此类情况仍然计费，OpenRouter 面临向用户收费却未交付内容的尴尬。行业惯例是不收费，但"生成了一半然后报错"的情况各家处理方式不同。请明确您的定义边界，以及对应的 HTTP 状态码和错误响应格式。

Sampling Parameters
采样参数支持情况
Required params — confirm all supported必须支持的参数（全部勾选方可接入）*
All five are mandatory. See openrouter.ai/docs/parameters for ranges and defaults.
注（参数技术说明）：
• max_tokens：限制生成的最大 token 数，与 context_length 区别在于：前者是输出上限，后者是输入+输出总上限。
• temperature：控制采样随机性，范围 [0, 2]。0 = 贪心解码（greedy），logits 除以 temperature 后再做 nucleus sampling。
• top_p：Nucleus sampling，保留累积概率前 p 的 token 集合进行采样。通常建议只调 temperature 或 top_p 其中之一。
• stop：遇到指定字符串时停止生成，支持字符串数组。必须在生成完该 stop token 后立即截断（不含 stop 字符串本身）。
• seed：固定随机种子以实现可复现生成。注意：同一 seed 在不同硬件/批次大小下可能不完全一致，应在文档中如实说明确定性保证级别。
Optional params — check all supported可选参数（支持的全部勾选）
注（可选参数技术说明）：
• top_k：每步仅从概率最高的 k 个 token 中采样，可与 top_p 叠加（先 top_k 再 top_p）。
• frequency_penalty / presence_penalty：OpenAI 定义的加法惩罚。frequency 按词频惩罚，presence 对已出现词一律惩罚，范围 [-2, 2]。
• repetition_penalty：HuggingFace / vLLM 风格的乘法惩罚（>1 = 惩罚），与 frequency/presence_penalty 语义不同，不能混用。
• min_p：过滤概率低于最高概率 × min_p 的 token，是 top_p 的变体，动态调整截断阈值。
• logit_bias：直接修改特定 token 的 logit 值，用于强制/禁止特定词汇出现。
• logprobs / top_logprobs：返回每个生成位置的 log 概率，用于评估和不确定性估计。
• response_format：强制输出为 JSON（{"type":"json_object"}），底层通常是 constrained decoding。
• structured_outputs：严格 JSON Schema 约束输出，需要 grammar-constrained generation（如 llama.cpp GBNF grammar、vLLM xgrammar）。
• tools / tool_choice：Function Calling——模型输出结构化 tool call 请求，由客户端执行后返回结果。

Support tool calling with streaming? Well tested or beta?
注：Tool calling 是 Agent 和 RAG 应用的基础能力。Stream 模式下实现尤为复杂：tool_calls 字段需要在多个 SSE chunk 中累积拼接（index / id / type / function.name / function.arguments 分别在不同 chunk 中逐步填充），客户端需要做状态机解析。

Structured outputs (JSON Schema)结构化输出（JSON Schema 约束解码）
JSON Schema structured output? Always working even with streaming?
注：response_format: {"type":"json_object"} 只要求输出合法 JSON，而 structured_outputs（OpenAI 2024 年引入）要求严格符合指定 JSON Schema（字段类型、required、enum 约束）。实现方案：① Grammar-constrained decoding（如 llama.cpp GBNF、outlines 库、vLLM xgrammar），在解码阶段屏蔽不合法 token，保证 100% Schema 合规；② Post-processing（生成后校验/修复），不能保证 100% 合规。请说明您采用哪种方案，以及 streaming 模式下是否同样可靠（需增量验证 JSON）。

Operational requirements — please confirm运营要求确认*
Let OpenRouter know if these cause latency or QoS issues on your end.
⚠ 注（两条不可协商的硬性技术要求）：
① OpenRouter 只发 streaming 请求（"stream": true）：您的 streaming 实现路径必须是生产级别的。理由：OpenRouter 的前端是实时流式 UI，non-stream 模式无法提供良好用户体验，也无法实现首 token 延迟的可见性监控。这意味着您的 non-stream 代码路径实际上几乎不会被调用，但仍需实现（某些健康检查和测试会用到）。
② 每次响应必须返回 usage 字段：包括 stream 模式最后一个数据 chunk。这是计费和路由质量监控的数据来源。若您的服务在高负载下偶尔省略 usage，会导致 OpenRouter 侧计费数据丢失——这是严重的集成问题，可能导致您被降级路由或下线。
若这两条要求会对您的服务产生延迟或 QoS 影响（例如计算 usage 本身引入延迟），请在备注中说明，OpenRouter 团队可以共同讨论解决方案。
